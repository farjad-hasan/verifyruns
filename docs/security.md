# Security

## Reporting

Email **farjad.developer@gmail.com** with "VerifyRuns security" in the subject. Please do not open a public issue for anything exploitable. You will get a reply within a few days; fixes are tracked as OpenSpec changes in this repository once they are safe to discuss.

## Current posture (2026-09-05, Cloudflare Workers build)

- Passwords (2026-08-31): PBKDF2-SHA256 via WebCrypto, 600,000 iterations (OWASP guidance), per-user 16-byte salt. Each stored hash carries its own iteration count; verification uses the stored count and a successful login against a weaker hash transparently re-hashes at the current strength — no bulk migration. Login performs the same PBKDF2 work for unknown emails as for known ones, so timing does not reveal whether an account exists. (During the upgrade window, an account still on a weaker stored hash verifies at its stored cost while unknown emails burn the current cost — that residual asymmetry disappears as hashes upgrade on login.) The upgrade write is a compare-and-swap on the exact hash the password verified against, so it can never overwrite a concurrent password reset. If the runtime refuses the iteration count (Cloudflare has historically capped PBKDF2 at 100,000), the worker caps itself and logs it rather than failing logins. **Verified live 2026-09-01:** production still refuses 600k (`NotSupportedError: iteration counts above 100000 are not supported`); the fallback engaged, registration and login worked, and the stored hash records `100000` — the effective strength on Cloudflare until the platform lifts the cap, at which point hashes upgrade to 600k transparently on next login.
- Sessions: HS256 JWT, 7-day expiry, no refresh. Tokens carry the user's `token_version`; a password reset increments it, so every previously issued session — including a stolen one — stops authenticating immediately. Tokens issued before this scheme are grandfathered as version 0 and die on the owner's first reset.
- Rate-limit identity (2026-08-31): the client IP is read from `CF-Connecting-IP` only, which Cloudflare sets and the caller cannot choose. `X-Forwarded-For` is never consulted — Cloudflare appends the real IP to a client-supplied value, so its first element is attacker-chosen. Off-Cloudflare, requests without the trusted header share one collective bucket.
- Password reset: `POST /api/auth/forgot` always answers 200 (no account enumeration) and, for a real account, emails a one-time link via Resend. Only the SHA-256 of the 32-byte token is stored; it expires after one hour, a newer request cancels older links, and a used token is refused. Consumption and the password change are one transaction, conditional on the token still being valid after hashing; concurrent reuse has exactly one winner. The reset endpoint shares the auth rate limiter. On a host without `RESEND_API_KEY`/`ALERT_FROM` the endpoint answers 503 and the page says so.
- Secrets at rest (bearer tokens, Airtable PATs, Postgres connection strings, alert-channel targets): AES-256-GCM under a single `ENC_KEY` held as a Worker secret; never returned to clients beyond the last four characters.
- Webhook secrets: 32 random bytes, URL-safe; public status tokens: 24.
- Egress (`egress-lockdown`, shipped): destinations whose host is a literal loopback, private, link-local, unspecified or cloud-metadata address (or `localhost`) are refused at save time and again before every fetch unless the self-host switch `VR_ALLOW_PRIVATE_EGRESS=1` is set; redirects are not followed; each HTTP response or Airtable page is capped at 5 MB with a 20 s request timeout (a multi-page read can take longer overall). DNS names are not resolved on Workers — for named hosts the guarantee is the platform's own network, which cannot reach private ranges.
- Rate limits: `/api/auth/*` per IP, `/api/hook/*` per secret (120/min each), Check creation and channel tests per user (60/min per operation bucket). Best effort — counters live per isolate, not globally.
- Postgres connector: single `SELECT`/`WITH` statement (no semicolons), wrapped as a subquery, with `default_transaction_read_only = on` on the session. Use a read-only role anyway. TLS is on unless the connection string says `sslmode=disable`, and the connector never downgrades on its own; on the hosted build the platform verifies server certificates against public CAs only (private-CA providers such as Supabase fail fast with an explanation rather than connect unverified; publicly-signed ones such as Neon connect over TLS normally).
- Data minimisation (`data-minimisation`, shipped): runs keep a fingerprint and a SHA-256 of the newest record, not rows; raw samples are opt-in per Check and expire after ~30 days. Details in [what-we-store.md](what-we-store.md).
- All destination reads are server-side; the browser never touches a destination.
- Headers (2026-08-30): every API response carries HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `Cache-Control: no-store`. The site (`frontend/public/_headers`) serves a Content-Security-Policy that runs scripts from its own origin only, connects only to itself and the API, and refuses framing — the backstop for the session token living in local storage.
- Alert targets are validated like destinations (2026-08-30): Slack/Discord webhooks must be public `http(s)` URLs under the same egress policy; email targets must be addresses.
- Alert delivery (client-readiness hardening): verdicts and notification transitions are committed with a durable outbox event. Events retain encrypted channel targets and are delivered in order per Check under expiring leases. Refused or interrupted attempts are retried by the scheduler with backoff (one minute, increasing to fifteen minutes), without requiring another workflow run. One accepted channel completes the event; failures remain recorded on the original run and increment `meta.alert_delivery_failures`. Provider acceptance is not inbox receipt. A crash between provider acceptance and acknowledgement in D1 can duplicate delivery. Snooze pauses pending delivery, removed targets are not retried, and deleting a Check removes its pending notifications.
- Manual runs: the run ID and manual trigger are persisted before the queued response. Immediate processing is an optimization; the scheduler resumes abandoned work after the two-minute renewable lease expires. A recorded run is reconciled without a second destination read.

- Monitoring: `GET /api/health` answers 503 when the cron has not ticked within 10 minutes; a scheduled GitHub Actions job probes it every 30 minutes and emails the owner on a red run. CI runs the worker suite and a frontend build on every push.

## Known gaps, tracked

- No email verification or account lockout.
- Rate limits are per isolate; a determined caller can exceed them across isolates.
- The session token lives in local storage (readable by any script that runs on the page); the CSP is the mitigation, an httpOnly cookie the upgrade.

Self-hosters: `VR_ALLOW_PRIVATE_EGRESS=1` disables the address checks — only set it on a host where every user is trusted.
